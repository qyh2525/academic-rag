# 学术论文 RAG 检索消融实验报告

> 验证"BM25 + 向量混合检索 + Cross-Encoder 精排"两阶段架构的有效性,通过中英对照评测发现单一指标无法暴露的工程问题。

## 1. 实验设置

| 项 | 值 |
|---|---|
| 数据源 | 30 篇 arXiv RAG 主题论文(2019-2026) |
| 向量库 | Chroma + BAAI/bge-m3(1024 维多语言 embedding) |
| 切分 | RecursiveCharacterTextSplitter,800 字符/chunk,3321 个 chunks |
| 精排模型 | BAAI/bge-reranker-base(cross-encoder) |
| 检索架构 | 召回 top-20 → 精排 top-4 |
| 评测集 | 中英各 20 题,覆盖 20 篇论文(每篇 1 题) |
| 评测集构造 | 手工筛选 + LLM 辅助生成(DeepSeek-V4)+ 三类陷阱设计 |

### 评测集陷阱设计

为了让消融实验能拉开差距,刻意设计三类题:

| 陷阱类型 | 数量 | 设计意图 | 例子 |
|---|---|---|---|
| 🟦 BM25 友好 | 11 题 | 含强专有名词(如 ColBERTv2 / FLARE) | "What does FLARE stand for?" |
| 🟢 向量友好 | 3 题 | 纯语义描述,不含原文关键词 | "What pattern did authors observe regarding position of relevant information in long contexts?"(命中 *Lost in the Middle*) |
| 🟨 混合友好 | 6 题 | 关键词 + 语义结合 | "How does CRAG handle suboptimal retrieved documents?"(CRAG 关键词 + 机制描述) |

## 2. 实验结果

### 英文评测集 20 题

| 方案 | Recall@4 | Recall@20 | MRR | 单题耗时(ms) |
|---|---|---|---|---|
| 纯向量 | 1.000 | 1.000 | 0.975 | 840 |
| 纯 BM25 | 0.900 | 1.000 | 0.818 | 35 |
| **混合 RRF** | **1.000** | **1.000** | **1.000** | 225 |
| 混合+精排(完整方案) | 1.000 | 1.000 | 0.975 | 8425 |

### 中文评测集 20 题(query 中文、文档英文,跨语言场景)

| 方案 | Recall@4 | Recall@20 | MRR | 单题耗时(ms) |
|---|---|---|---|---|
| 纯向量 | 1.000 | 1.000 | 0.942 | 890 |
| 纯 BM25 | **0.250** 💥 | **0.250** | **0.250** | 30 |
| 混合 RRF | 1.000 | 1.000 | 0.867 | 235 |
| **混合+精排(完整方案)** | 1.000 | 1.000 | **0.967** | 10440 |

## 3. 三个关键发现

### 🎯 发现 1:BM25 在跨语言查询下彻底失效(Recall@4: 0.900 → 0.250)

英文 query 下 BM25 几乎全命中(R@4=0.9),但同样的题用中文问下来 R@4 暴跌到 0.25。

**根因**:BM25 是字面 token 匹配。中文 query 的 token 与英文文档完全不重叠,只有 query 中夹杂的英文专有名词(ColBERTv2、FLARE)还能锚定。在 BM25 视角下,中文 query 几乎等同于"空 query"。

**工程启示**:**纯关键词检索在多语言系统中存在根本短板**,这是单一指标"R@4 看着还行"无法暴露的问题 —— 必须靠对照评测才能发现。

### 🎯 发现 2:RRF 融合不是万灵药 —— 失效路径会污染融合结果

中文场景下,混合 RRF 的 MRR (0.867) 反而**低于纯向量** (0.942)。

**根因**:BM25 失效后,它依然往 RRF 融合里贡献"无意义的排名",拖累了向量那一路的优质结果。RRF 按排名加权,无法识别某一路是否真的有信号。

**工程启示**:**生产 RAG 系统应该做"检索路径健康度监控"**,当某一路的得分分布异常(如 BM25 在中文 query 下所有候选得分接近)时,自动降权或屏蔽该路径,避免拖累融合质量。

### 🎯 发现 3:Cross-Encoder 精排的价值高度依赖召回质量

| 场景 | 混合 RRF MRR | +精排后 MRR | 精排增益 |
|---|---|---|---|
| 英文(召回完美) | 1.000 | 0.975 | **-0.025** ⚠️ |
| 中文(BM25 失效) | 0.867 | 0.967 | **+0.100** ✅ |

英文场景下,混合 RRF 已经把正确答案稳定排到 top-1,精排反而引入微小噪声(把第二位的"语义相近"文档排到了第一)。
中文场景下,BM25 失效后混合 RRF 的 top-1 位置不稳定,精排凭借 cross-encoder 的跨语言语义对齐,把 MRR 拉回 0.967。

**工程启示**:**精排不是无脑加的链路** —— 它能"修复差的召回",但对"好的召回"可能是负优化。生产系统可以加 query 难度判断:简单题走 hybrid(225ms),难题走 hybrid+rerank(8.4s),做**自适应延迟优化**。

## 4. 性能/延迟分析

| 方案 | 平均延迟 | 适用场景 |
|---|---|---|
| 纯 BM25 | 30ms | 极致延迟,但仅适合关键词命中明确的场景 |
| 纯向量 | ~860ms | 通用,语义优先 |
| 混合 RRF | ~230ms | **性价比最高**,英文 query 已足够 |
| 混合+精排 | 8400-10400ms | 复杂/跨语言 query,延迟换精度 |

完整方案延迟 8.4-10.4s/题,主要瓶颈是 cross-encoder 对 20 个候选逐一打分(O(N) 推理)。后续可优化方向:
- batch 推理(20 个候选并行)
- 模型量化(bge-reranker-base int8 量化)
- 召回降到 top-10(精度损失换延迟)

## 5. 局限与后续工作

1. **评测集偏简单**:答案 source paper 在大多数题中能从关键词直接定位,真实"刁钻题"(同主题多篇论文混淆)未覆盖
2. **未评估生成质量**:本评测只覆盖检索阶段(论文是否找对),没有评估 LLM 基于检索内容生成的答案质量(RAGAS / ARES 路线)
3. **未做查询难度自适应**:当前精排无条件触发,生产环境应该按 query 复杂度动态选择检索路径

## 6. 一句话总结

> 通过 4 组消融 × 中英对照评测,验证了"BM25+向量混合 → Cross-Encoder 精排"两阶段架构在中英场景下的差异化价值,**并发现了 RRF 失效路径污染、精排过度优化** 两个生产系统易忽视的工程问题。
